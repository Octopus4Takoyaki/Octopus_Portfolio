Method · Premise

方法论总纲：观测不等于真相

本框架及配套文档（02 分发链路、03 指标方案）共享一个前提：观测到的数据，不等于我们想知道的真相，中间隔着偏差和噪声。

  • 偏差：系统性扭曲。曝光多的资产数据多、位置好的资产点击多、小样本比率虚高。
  • 噪声：随机波动。样本少波动大。

在这个前提下，框架里任何一个指标或操作，都回答四个子问题之一：

子问题朴素问法在本框架的落点
效度量的对不对区分「资产质量」和「分发表现」；调用量不进质量分
信度量的稳不稳在线比率取 Wilson 置信下界
因果关系真不真影子期对账「质量分与在线完成率」的相关性
估计参数怎么来维度权重、质量乘数在影子期标定

这样，框架里每一个数字（质量分、乘数、权重）都有处可归，不是空降。

Premise

一个前提：资产质量不等于分发表现

Agent 资产质量分发表现
回答的问题这个 Agent 本身好不好、可不可靠、安不安全这个 Agent 分发后被选用、被完成得怎么样
评估对象Agent 的能力与行为（任务执行轨迹）Agent 进入分发后的统计结果
是否依赖分发环境不依赖，可离线评估依赖，只能在线观测
典型信号任务完成率、工具调用正确率、推理质量、鲁棒性、安全合规调用量、失败率、退出原因、曝光转化率、token 消耗

两者的关系：资产质量是分发的前提；分发表现是资产质量在真实流量里的投影，用于校准和触发重评，本身不是质量。

一句话：先回答「它值不值得被分发」，再回答「它分发后表现如何」。前者是后者的基础。

Positioning

产品定位

一句话定位

这是 Agent 资产生态里的「质量准入与续用判断层」：在资产进入分发之前，判断它本身是否达标；在分发持续期间，判断它是否还值得继续被分发。它不负责「把谁排第一」，只负责「谁有资格被排」。

解决什么问题

平台现状有两个问题：用户以关键词检索为主，能搜到的不一定匹配；头部资产反复被分发，长尾资产能力达标也难触达。两者的根因是同一个：平台没有「资产本身好不好」的独立标准，只能用「被用得多不多」当代理。而调用量反映的是历史曝光的累积，不等于质量。本框架补的就是这个缺。

框架回答三个问题

  1. 能不能进：资产质量是否达到准入门槛（能力达标 + 安全合规硬门槛）。
  2. 值不值得继续分发：质量分作为分发排序里的质量项，以及在线哨兵是否触发重评。
  3. 该不该退出：重评后质量分是否跌破退出线，而不是「失败率高就下架」。

服务谁

使用方拿到什么用途
分发链路质量分准入门槛 + 排序里的质量项
创作者质量归因（为什么是这个分）迭代改进的依据
平台运营治理依据、供给缺口信号生态治理

边界：不做什么

  • 不做排序。排序由分发链路做，框架只提供质量输入。
  • 不做匹配判断。「合不合」是分发链路的事，框架只判「好不好」。
  • 不做创作者评价。评估的是资产，不是人。
  • 不面向终端用户展示。不变成界面上的「官方评分」。
Industry Basis

行业已有做法

Agent 质量评估在 2024–2026 年已形成方法论共识。本框架做的是「适配 + 裁剪」，不是发明。

三条共识

共识一：评估对象是执行轨迹，不是最终答案。Agent 的一次运行是「输入 → 推理 → 工具调用 → 观察 → 输出」的多步轨迹。只看最终答案会漏掉多数问题：工具选错、参数传错、循环重试、推理链断裂，这些都不出现在最终文本里。Langfuse 把 Agent 质量拆成四维：轨迹、工具使用、任务完成、多轮质量。

共识二：评估方法分三层，是层不是替代。确定性代码检查（可判定的事，毫秒级）；LLM-as-judge（语义判断，需人工标注校准）；人工标注（建立真值、校准 judge）。

共识三：离线评估和在线观测回答不同问题，缺一不可。离线评估在发布前跑，抓回归；在线观测持续跑，抓漂移和长尾。

Evaluation System

评估对象与七个维度

评估对象

本框架的评估单位是：给定一个任务，Agent 的一次执行轨迹（输入 → 推理 → 工具调用 → 观察 → 输出）。失败率、退出原因不是质量本身，因为它们把大量轨迹粗粒度聚合，丢掉了轨迹内部的信息。一个失败率 40% 的 Agent，失败可能是「工具选错」（可修），也可能是「推理链断裂」（难修）——只有打开轨迹才能判断。

对应 WorkBuddy：Agent 的「工具」就是它调用的 Skill / Plugin / MCP / 工作流，「轨迹」就是它执行任务时的调用序列和中间状态。平台已有对话日志和工作流编排能力，轨迹采集有现实基础。

七个评估维度

维度回答的问题核心指标评估方法
Q1 任务完成目标达成了吗任务成功率、稳定性 passᵏ、进度率有真值用确定性比对；无真值用 LLM-as-judge
Q2 推理与规划想得对不对、计划守不守得住计划质量、计划遵循度LLM-as-judge 为主，人工抽检校准
Q3 工具/技能调用用对工具了吗工具选择准确率、参数正确率、冗余调用率确定性检查（工具名、参数 schema）
Q4 轨迹效率路径高效吗步数 vs 最少步数、循环率、token/任务、时延 p50/p95确定性检查
Q5 记忆与多轮跨轮记得住吗上下文保持、目标漂移、会话解决轮数LLM-as-judge；无记忆类记 N/A
Q6 鲁棒与恢复出错能自愈吗错误恢复率、扰动稳定性、故障注入降级表现确定性（故障注入）+ 人工评审
Q7 安全与合规干不该干的了吗注入/越权抵抗、敏感数据泄露率、政策合规率确定性（红队用例）+ 人工终审
取舍：七维不要求每个资产跑满。权重不公开精确数值（防针对优化），核心权重压在 Q1/Q3/Q6/Q7 这几个难以用行为数量操纵的维度上。
Method & Pipeline

评估方法与流水线

三层方法

层适用成本/时延示例
确定性代码检查可判定的事毫秒级、近零成本工具是否调用、参数是否过 schema、步数是否超预算
LLM-as-judge语义判断模型成本、秒级计划是否合理、推理是否连贯、答案是否切题
人工标注真值与校准专家时间、天级建立真值、校准 judge、裁决歧义或安全关键轨迹

分工：代码检查跑在每条轨迹上；judge 跑在需要语义判断的子集上；人工处理分歧和低置信度样本，并反向校准 judge。

评估流水线

  1. 测试集构建：优先从真实业务数据挖掘；冷启动用人工示例 + self-instruct 生成。覆盖常规、边界、对抗三类场景。
  2. 执行：在沙箱中运行 Agent，采集完整轨迹。
  3. 打分：按七维 + 三层方法计算分维度得分。
  4. 归因分析：对失败用例归因（工具选错 / 参数错 / 推理断 / 安全违规），定位瓶颈。
  5. 迭代：修正后重跑，形成「评估 → 优化 → 再评估」闭环。

约束：测试集质量决定评估结论的上限。评估资产质量，本质是评估「Agent × 测试集」这个组合。

Into Distribution

质量如何支撑分发决策

准入：质量是门槛

资产先通过质量评估（Q1 达标 + Q7 硬门槛），才获得分发资格。评测方式按资产状态分三种，都用平台已有资源：

资产状态评测方式真值来源
已有流量在线评测（对话日志挖矿）用户行为：满意/重试/换资产/退出
新资产/长尾合成任务评测模型自动生成任务 + LLM-as-judge
安全/关键场景人工标注终审人工构造真值

质量分：分发排序里的质量项

七维合成一个质量分（带分维度归因），在精排里作为匹配度的乘数：

最终得分 = 匹配度 × 质量乘数 + 边际热度 × 小权重
  • 匹配度回答「合不合」，占主导。
  • 质量乘数回答「好不好」，初始 0.8–1.2，影子期标定。
  • 新资产质量分置信度低时，乘数收敛到 1，先靠匹配度被选中。
  • 长期由 learning-to-rank 学权重，人工乘数退位。

在线观测：哨兵与校准

任务书给的元数据（调用量、失败率、退出原因、token、评分、转化率）不是质量，是在线哨兵信号：失败率、token 等异常时触发重评（重跑离线测试集），而不是直接改质量分；在线结果（复用率、任务完成）与离线质量分对账，校准评估和 judge。

退出：重评驱动

级别触发条件动作
降权哨兵异常，重评后质量分跌破 0.45质量项压至下限，保留曝光
暂停分发重评后质量分跌破 0.30，或安全重评不通过撤出主动曝光，保留资产页
下架安全硬违规（立即）；或暂停满 90 天且创作者无修复移出资产目录
Cold Start

冷启动与置信

  1. 准入不依赖调用量：新资产通过质量评估（测试集达标）即可准入。调用量从来不是质量的组成部分。
  2. 在线比率取置信下界：失败率、转化率等在线比率用 Wilson 置信下界，小样本向保守收缩，既不被早期差评钉死，也不因小样本高分被过推。
  3. 观察池：新资产进入观察池，获得保底探索流量（占分发总量 2%–5%），积累在线信号，样本充足后转正式池。
Trustworthiness

平台是否可采信该框架

评估框架最大的风险不是「不准」，而是「不准但没人发现」。平台采信该框架，需要五条判断依据同时成立：

判断依据校验动作
可解释质量分可归因到七维的具体得分和测试用例，创作者能核对「为什么是这个分」
抗操纵调用量不进质量分；核心权重压在难以操纵的 Q1/Q3/Q6/Q7
冷启动公平准入不依赖调用量；在线比率取 Wilson 下界
后验一致影子期验证「离线质量分与在线完成率、复用率」的相关性，达标才上线
可回滚质量分对分发的影响统一走「质量项」出口，逐日快照，异常可回退

采信流程：影子期（只算不出声，对账后验一致性）→ 灰度期（10%–30% 流量、质量项封顶）→ 全量（护栏触发自动回滚）。五条中任何一条被证伪，框架都不应被采信上线。

Cost

评测如何落地，成本在哪

任务书给的可用元数据（名称、描述、调用量、评分、token 消耗、失败率、退出原因）几乎全是分发观测，没有一项能直接支撑资产质量评估。这是本框架和「拿现成分发数据凑质量分」的关键区别。

但资产质量评估不一定要靠长时间人工离线评测。三种评测方式覆盖全部资产，且都用平台已有资源：

评测方式靠什么人工成本
在线评测对话日志 + 需求理解层结果 + LLM-as-judge低
合成任务评测通用大模型生成任务（self-instruct）+ 工作流编排跑轨迹 + LLM-as-judge 打分低
人工标注安全/关键场景终审高，仅少量场景

真正的增量投入只有一项：合成任务评测的流水线（自动生成任务 → 沙箱执行 → 打分），用平台已有的通用大模型和工作流编排就能搭。

边界：合成任务评测是冷启动的起跑器，不是永久替代。合成任务是模型编的，编不出真实用户才会踩的边界 case；资产攒够真实流量后，应切到「对话日志挖矿」，那才是真值。
